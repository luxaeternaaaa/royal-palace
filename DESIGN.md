# Royal Palace — design context

## Purpose
Russian presentation website for families planning a celebration at Royal Palace, Astana, Chingiz Aitmatov 58. The single conversion is a prepared WhatsApp enquiry; no booking, backend, payment or automatic message sending.

## Visual direction
A clear presentation of the actual venue: real photography, readable controls and restrained green/champagne surfaces that suit its interior. At the user's explicit request, the confirmed main-hall photograph fills the hero background again. White text and upright champagne emphasis sit over a directional dark scrim; keep the image edge to edge rather than reverting to a split photo panel. Its primary action starts with hall comparison; discussing the celebration remains directly available. Display type gives hierarchy; plain, specific headings carry the information. Short headings have no trailing full stop; body copy stays simple and welcoming. Do not recreate a logo or treat a newly designed monogram as the venue's brand. The authentic Instagram JPG stays unchanged; the header renders the original artwork in palace green with a transparent background, using the SVG filter described in `docs/logo-source.md`.

The earlier refinement used Impeccable, Design Partner, Frontend Design Premium and Awesome Design MD. The current pass is led by UI UX Pro Max, with Design Partner and Frontend Design/Premium. Verified local searches matched Restaurant/Food Service and Wedding/Event Planning. Their useful guidance is real venue photography, clear hierarchy, progressive disclosure and visible focus; generic red/pink palettes, script fonts, planning tools and testimonial carousels do not fit the established venue or available evidence and are not applied. Keep the existing self-hosted fonts and identity rather than adopting every database suggestion. The earlier Airbnb reference informs photo-first composition and readable controls only.

The medium photo action requests photos and seating options; the small-hall action also asks for its unconfirmed capacity. No duplicate event tabs before the form. Max content width 1280px. Responsive 320px–1920px; no hidden essential actions. Primary touch targets at least 44px. The light sticky header keeps a constant height per breakpoint, avoiding a layout jump while scrolling. Design and verify desktop and mobile together. Form actions target `#enquiry-form`, with a direct WhatsApp alternative inside the form and visible below the sticky header. Global scroll padding owns header offsets; do not duplicate it in form scroll margin. Native dialogs, native details for FAQ/optional fields, visible focus and reduced motion are retained. The message has one scroll container (the dialog), not an inner scrolling preview. Gallery supports real 2× image viewing and explicit retry; enquiry supports copy with manual fallback. The hero footer includes an image link with a gallery enhancement so the full photo remains available without JS. With JS disabled, form submission stays disabled and prefilled quick-request links remain usable. Evidence and actual coverage are in docs/verification.md.

The optional disclosure is labelled «Дополнительные детали», which remains accurate after the user has entered and collapsed a draft. FAQ uses the direct heading «Вопросы о банкете». Across the mobile/desktop breakpoint, transfer focus from disappearing navigation to its visible equivalent; retain ordinary focus outside navigation.

Keep the recognised WhatsApp SVG filled, with no inherited outline. Hero height must grow with user text spacing; its normal photograph and composition stay intact. Mobile scroll padding reserves space above and below focused actions for the header and floating contact button. Dark mobile navigation uses champagne focus outlines.

Gallery zoom is exactly twice the fitted image size, including portraits. Zoom moves focus to the pan area; resize returns the whole photo. A successful retry restores its failed thumbnail, and a hidden modal must not initialise an image request. Photo cards remain native image links without JavaScript. Mobile HTML navigation and a direct-contact explanation are present until successful app initialisation; inactive floating controls cannot receive focus. Copy feedback belongs only to the currently open preview, never an older asynchronous operation. Preserve keyboard focus after copying. ## Motion

Motion supports reading and state changes. Canonical timing tokens live in `public/styles.css`: `--motion-ease` is `cubic-bezier(.22, 1, .36, 1)`, `--motion-fast` 180ms, `--motion-disclosure` 260ms, `--motion-reveal` 440ms and `--motion-photo` 600ms. Keep the initial hero, logo, navigation and form immediately available. Do not animate the hero photograph or continuously track scroll positions for decoration.

The independent optional `public/motion.mjs` observes below-viewport content once. Reveals use opacity; only content without interactive controls moves up to 8px. Animations have no fill mode or hidden CSS classes, so unavailable APIs, a blocked motion module or interrupted playback never hide content. Keyboard focus cancels the relevant reveal. Switching to reduced motion or printing cancels running reveals and disconnects pending observations. Reveals do not replay after scrolling back.

Native FAQ disclosures animate their content height and opacity only when `::details-content` and `interpolate-size` are supported. Other browsers retain native opening/closing. The form disclosure stays immediate so validation and focus never wait for animation. Dialogs, loaded gallery photos and the mobile menu fade in without changing hit areas; closing remains immediate to preserve focus behavior. Photo zoom and arrow feedback are limited to fine-pointer hover and are absent under reduced motion. Gallery image zoom still uses its existing exact 2× calculation. The existing sticky action degrades to ordinary navigation if IntersectionObserver is unavailable.

References: [Le Dome](https://ledome-banquet.kz/) informed restrained entrance and surface transitions; implementation uses the native disclosure enhancement documented by [Chrome for Developers](https://developer.chrome.com/blog/styling-details). Current executed checks and limits belong in `docs/verification.md`.

## Form contract
For a full enquiry, only event is required. The event, preview action and direct contact are shown first; hall/date/guests/wishes live in a native optional disclosure. Collapsing it preserves all values. Validation opens it before focusing an invalid optional field. Editing a full preview reopens it and returns to the form; quick-request return restores its own trigger. FAQ date/guest links reveal the relevant optional section. Blank date and guest count mean undecided, without confirmation checkboxes; invalid nonempty values receive field-specific Russian errors. Hall defaults to help choosing, expressed as «Зал: пока не выбрали» in the message; wishes are optional. The hall-assistance action explicitly adds its selection question instead of silently losing the user's intent. Quick requests for menu, viewing or hall photos/seating need no form details and must not read or change a draft form. Preview the exact message before opening WhatsApp. Date is a request, never confirmation. No personal data is stored, sent to this site or placed in analytics. Only explicit click opens WhatsApp; the user sends there manually. Current date uses Asia/Almaty (Astana, UTC+5).

Hall rows provide information and relevant photo actions; they do not ask for an uninformed selection. The confirmed main-hall photo opens in the existing gallery. FAQ seating questions add visible context without replacing event, date, guests, hall or wishes. Menu and viewing questions open their own short previews. Never add a viewing request unless chosen by the user. An unspecified date produces a conditions question rather than asking whether an unspecified date is free. A specific topic does not append unrelated questions. Preview/edit/copy do not submit anything. Explain booking once and use plain, welcoming copy elsewhere.

## Standing user preference: design workflow
For every future interface task, proactively apply the relevant installed design skills/plugins without requiring manual user activation. Choose by the actual task: Impeccable, Design Partner, Frontend Design/Premium and Awesome Design MD are available; explicit user requests determine which to apply. Do not run every skill by default, install unnecessary plugins or expand scope for process. Evaluate concrete clarity, typography, composition, authenticity and interaction states; do not treat a color or font alone as proof of AI authorship. For anti-template reviews, consult primary external design sources, check the actual rendered UI and fix confirmed patterns. Preserve the hackathon priorities and existing working behavior. Use one batched desktop/mobile inspection, one correction batch and one confirmation.
